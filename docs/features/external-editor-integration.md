# External editor integration

Minecraft Server Studio includes a local external-editor handoff foundation for
server folders, a path-redacted app-private handoff record, and
application-created exports. It is a convenience route from
the desktop application to an editor that already exists on the same computer;
it is not a cloud editor, remote-development service, file synchronizer, or
shell-command console.

## Implemented behavior

The compact external-editor preference surface discovers local Visual Studio
Code candidates and lets the user choose the active executable. Discovery is
limited to bounded standard, current-user, machine-wide, Insiders, portable,
and `PATH` layouts. The same selected Visual Studio Code executable serves the
safe-history export handoff. Native pickers provide explicit local `.exe` and
folder selection routes when automatic discovery does not provide the desired
candidate.

The handoff uses direct process arguments rather than a shell string. It can
open either:

- the selected local Minecraft server folder as an editor workspace; or
- a newly generated path-redacted app-private handoff record; or
- a verified existing output generated by the application, such as a supported
  local-history export, in the selected editor.

The app-private handoff record uses one fixed, validated private export path
and omits the server display name, root path, credentials, player data, and
configuration contents. It is generated only after a selected server record is
available. An existing-output handoff is enabled only after the corresponding
application-owned output exists. A folder handoff is enabled only after the
currently selected server folder has been validated by the server registry.

## Local preference and launch boundary

The selected editor is a local desktop preference owned by
`src/main/external-editor-service.cjs`. Its app-private atomic JSON record
stores only a validated executable path; the displayed label is derived locally.
It does not upload
an executable path, server folder, export content, credentials, or editor
configuration.

Before a launch, the application rechecks a canonical absolute `.exe` path, its
existing file identity, the selected local target, and the bounded string
limits. It resolves a selected path to its canonical local target before use.
It passes the workspace or output as a direct argument with
`shell: false` and does not accept arbitrary shell text, concatenated flags,
environment-variable expansion, remote URLs, or a command script from the
editor preferences.

Opening a folder makes that folder the editor workspace root. Opening an export
uses the real generated output rather than a preview or a guessed filename. The
application does not claim that an editor loaded extensions, understood a file
format, saved a change, or changed the local Minecraft server after the editor
process starts.

## Failure and recovery behavior

- **No Visual Studio Code candidate is found:** the handoff remains unavailable
  and the preferences surface explains that a local editor executable or folder
  must be selected before retrying. The application does not install an editor
  itself.
- **The selected editor is gone or no longer valid:** the saved selection is
  not silently substituted with a different executable. The user can refresh
  discovery or choose another local editor through the native picker.
- **The server folder or export no longer exists:** no editor process is
  started. The application reports the missing target and keeps the existing
  server or export record unchanged.
- **The editor process cannot start:** the application reports a concise safe
  launch error without treating it as a successful handoff. It does not fall
  back to a shell, a browser, or a remote editing service.

## Privacy and security considerations

External-editor integration is local-only. The feature does not contact a
network service, install an editor, transfer a server folder, upload an export,
read editor credentials, or add a browser extension. Its direct argument route
is intentionally separate from Minecraft server launch and command execution.

Server folders can contain configuration and plugin material that should be
treated as sensitive. The handoff therefore names the target before launch and
does not serialize server contents, protected credentials, or editor output in
the preference record. Launch and validation failures omit server and editor
paths from logs and local history.

## Current boundary

This foundation does not claim a complete export system, a generic editor plugin
ecosystem, a cloud workspace, collaboration, source-control integration, or
that every application record has already gained a generated-file handoff.
Unsupported or not-yet-generated outputs remain visibly unavailable rather
than being represented as files that can be opened.
